# ADR 0001：v2 架構（參照刷卡登錄雷達）

狀態：已採納（2026-11-06）

## 背景

v1（C 架構）把四大宗改成確定性 adapter，長尾 8 家由 Claude 例行任務每次開瀏覽器
現抓，`promotions.json` 直接寫入 `lifecycle`、`is_high_return`、`quota_status`。
問題：

- 回饋只從**標題** regex 取（`extract_reward`），門檻、每人上限、通路、付款方式全無。
- 額滿判定靠 AI 現場判讀，條件句（「額滿為止」）與已額滿聲明混淆；「10月份已額滿」
  在 11 月仍被當成額滿。
- 時間衍生狀態凍結在資料檔（與刷卡雷達 ADR 0001 問題一同類）。
- 全支付 adapter 寫死掃到 id 130，2026-11 實際到 153，漏 22 筆。

## 決策（Gary 2026-11-06 定案）

1. **LLM 抽三類**：回饋條件（回饋、門檻、每人上限、通路、付款方式、新戶限定）、
   名額與已額滿聲明、登錄／領券時點。一頁一次 `claude -p --json-schema`（Sonnet）。
2. **程式驗證**：引句逐字出現在條款；每個數字在引句裡找得到（千分位、小數、
   「2萬」、「一張／乙份」）；已額滿必須是已發生語氣，條件句一律不採用。
3. **已額滿帶範圍**：`SoldOut.scope_start/end`（「10月份」＝10/1–10/31）或只有範圍
   字樣（「首週」）。整檔額滿＝三者皆空。LLM 漏給範圍時由程式從引句補，避免把
   部分額滿標成整檔。前端以今天判斷是否「現在」額滿。
4. **整頁 registration**：任一子活動需登錄／領券即 required；條款完全沒有任何
   參加動作字樣時由程式判 not_required（不靠 LLM）。
5. **條款不在自家網站**（一卡通轉到合作銀行）標 `terms_source=external`，不放寬
   白名單去追第三方；沒有可讀文字標 `image`。兩者都不送 LLM。
6. 長尾能寫 adapter 就寫，寫不了標涵蓋缺口（Phase 3）。
7. 同 repo `v2` 分支、前端 Astro、本機 launchd 每日＋macOS 通知（Phase 4／切換）。

## golden 驗收

36 頁（四大宗各 9，含已額滿頁），兩個獨立標註者只讀原文副本，規格見
`golden/SPEC.md`。評分以「事實」為單位（回饋、門檻、上限、已額滿、登錄、是否優惠）。
diff 一律回原文仲裁，仲裁理由寫進該筆 `note`。

| 輪次 | 精確率 | 召回率 | 主要修正 |
|---|---|---|---|
| 初版 | 89.2% | 85.1% | — |
| 二 | 95.3% | 90.4% | 單筆上限納入、整頁登錄定義、無登錄字樣判 not_required、「折」單位 |
| 三 | 98.7% | 89.7% | 程式補額滿範圍字樣、「乙」、最高享 X 是回饋不是上限；golden 補記保守漏標 |
| 全量 | 98.7% | 90.5% | 「乙」修正實際生效（前一版字串替換沒套上）；贈品數量評分只比有無 |
| 長尾後（57 頁） | 98.9% | 87.8% | 長尾 7 家加入；Pi 拍錢包多層回饋召回偏低 |

已額滿：精確率／召回率皆 100%。召回不足主要是標題型宣稱值（「最高 13%」為疊加
加總）與抽獎門檻，影響小於錯標。

## 成本與額度

首次全量 217 筆活動、LLM 抽取 170 頁（Sonnet）約 US$7.4，平均每頁 US$0.04；之後只有
條款內容變動的頁才重算。2026-11-06 全量途中撞到訂閱用量上限，之後 `LimitReached`
讓整輪在第一次就停止（exit 6），不再把剩下的頁逐一送出。
